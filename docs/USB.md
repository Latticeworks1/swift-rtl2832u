# The USB layer

## Conditions

The RTL2832U enumerates as a high-speed USB device. All control of the chip, including the demodulator, the tuner behind it, and the sample clock, travels as vendor control requests on the default pipe. All samples travel in one direction on bulk endpoint 0x81 as interleaved unsigned 8-bit in-phase and quadrature bytes. The tuner is reached through an I2C bridge inside the demodulator, which must be switched on for the duration of each tuner transaction. Two consequences shape the layer. Register access is a sequence of small blocking transactions whose order matters, and sample delivery is a continuous stream whose buffers must never run dry, because the ADC delivers samples at a fixed rate whatever the host is doing.

The host side adds three conditions. The device is removable at any instant, so every operation must be able to fail with a disconnection and every resource must be released in a defined order. The sample consumer is a signal chain that tolerates no gaps it has not been told about, so any discontinuity in the stream must be visible to it. The application runs on macOS with no kernel extension, so the layer speaks to the hardware through IOUSBHost, and the work of the driver is bounded by what that framework exposes: a device object, an interface object, and pipes on which requests are queued and completed asynchronously.

## Ownership and discovery

The transport finds the dongle by iterating the IOUSBHostDevice services in the registry and selecting those with vendor identifier 0x0bda and product identifier 0x2832 or 0x2838. The filter is applied in code because an idVendor key in the matching dictionary matches nothing on the development machine. Matches are sorted by location identifier so that an index names the same physical port from one run to the next. Opening a device creates an IOUSBHostDevice for control requests and an IOUSBHostInterface for interface 0, which together claim interface 0 for the process. Both objects register an interest handler, and the registry's termination message on either one marks the link lost exactly once, however many services report it, and calls the detach handler supplied by the device layer. The dongle events in `Radio/DongleEvents.swift` use IOKit first-match and terminated notifications on the same device class, drain the existing matches when they are armed, and identify a departure by the registry entry ID recorded at arrival. A failure at any step of opening releases whatever was already acquired, so a thrown error leaves no partial ownership. Closing stops the stream, drops the bulk pipe, then destroys the interface and then the device.

## Register access

Every register access is a vendor request with bRequest 0 and a timeout of 0.3 seconds, and a transfer that moves fewer bytes than requested is an error. The chip's registers fall into blocks named by the high byte of wIndex: demodulator, USB, system, tuner, ROM, infrared and I2C. Reads set that byte alone, writes also set 0x10 in the low byte, and multi-byte values are read little-endian and written high byte first. The demodulator's own registers sit in pages. A demodulator access puts the register number in the high byte of wValue with 0x20 in the low byte and carries the page in wIndex, with 0x10 added to the page for a write. Each demodulator write is followed by a read of page 0x0a, register 0x01, whose result is discarded, and the error of the write itself is reported after that read. Demodulator page writes are refused with a pipe error until the demodulator has been powered through two writes to system registers 0x300b and 0x3000, as was observed on a Blog V4 before those writes were made. Baseband initialization therefore includes the same two writes, ahead of its first demodulator access, and the tuner probe repeats them.

Tuner access goes through the I2C bridge. Setting demodulator page 1, register 0x01 to 0x18 connects the bus to the tuner and 0x10 disconnects it, and a scoped helper turns the bridge on, runs its body, and turns it off again on every exit, reporting the body's error when both the body and the switch-off fail. The tuner probe reads register 0x00 at addresses 0x34 and 0x74 and records the byte or the failure for each. The value 0x69 identifies the R820T, R820T2 and R828D family, and the probe infers nothing beyond that match, because the family shares the check value and says nothing about the board or its crystal.

## Baseband configuration

The chip is configured once, when the dongle is opened. Initialization sets the USB endpoint, resets the demodulator, clears the intermediate-frequency and offset registers, loads a sixteen-coefficient FIR, and turns the demodulator's own gain loop off. A second step puts the chip in the arrangement the R82xx tuners need, with the zero-IF path off, the in-phase input only, an intermediate frequency of 3.57 MHz, and spectrum inversion. The intermediate frequency and the sample rate are both written as 22-bit fractions of the demodulator crystal, which is nominally 28.8 MHz and can be scaled by a parts-per-million correction. The resampler realizes rates above 225 kS/s and up to 3.2 MS/s, excluding the band from 300 to 900 kS/s, and the function returns the rate actually realized, which differs slightly from the request because the ratio is quantized. A soft reset follows every rate change. The tuner's reference is a property of the board: the Blog V4 profile uses 28.8 MHz and the generic profile uses 16 MHz, and the tuner's frequency synthesizer is programmed from that value.

## Streaming

The stream keeps a fixed number of bulk requests queued so that the controller always has a buffer to fill. At 2.4 MS/s the block length, derived from a block duration of 20 ms rounded to whole 512-byte packets, is 96,256 bytes, which is 20.05 ms of samples, and the queue depth of 8 holds about 770 kB, or roughly 160 ms. Each completion hands its buffer to a handler on the pipe's completion queue, and the same buffer is resubmitted only after the handler returns, so the handler's work counts against the time before that buffer is available again. Just before a stream starts, the endpoint control register is pulsed so that the next bulk read begins on a sample boundary, and the first buffer after the start is discarded. The handler's block is the transfer's bytes, and the router copies them, two bytes per complex sample, into the queue of the current capture.

Stopping a stream is the delicate step, because a completion that is already running can queue one more request after the abort. Every request is registered with a gate before it is queued, and registration fails once the gate is closed. A stop closes the gate and then reads the pending count with sequentially consistent ordering, so either the late request is refused or the stop sees it pending. The stop aborts the pipe, repeats the abort while requests remain, and waits up to two seconds for the count to reach zero, so that no handler starts after a successful stop and the caller may then reconfigure the device. A stop that hits the deadline reports failure and leaves the buffers alive until the pending completions return, so late completions never touch freed memory. A transfer that fails closes the gate and reports its error code once.

A sample-rate change stops the stream, reprograms the tuner bandwidth, the resampler and the local oscillator, flushes the chip's FIFO, and starts a new stream. Every block carries the rate it was captured at and an epoch that rises with each such change. A change of center frequency alone leaves the stream running, and the samples captured during the retune settle within a few blocks. The device core serializes all control calls with one lock, because two interleaved sequences through the I2C bridge would corrupt each other. The radio is an actor that runs on a dispatch queue of its own, so its controls are asynchronous calls that do not occupy the caller's thread, and it delivers samples as a sequence of captures, each a run of blocks that are contiguous in time at one center frequency and one sample rate. A router on the completion queue copies each block it keeps into the queue of the current capture, which holds eight blocks and discards the oldest when the consumer falls behind. The router never waits for the consumer, so a slow consumer loses blocks from its own queue and does not hold up the completion queue. Each block carries a sequence number, so a gap in the numbers shows blocks that queue discarded. Samples lost at the controller, when the completion queue is stalled for longer than the queued requests can cover, leave the numbering intact.

## Acquisition integrity

A stream can be complete at one level and damaged at another, so each block carries an acquisition record whose fields vary independently, next to the sequence number that reports whether the consumer's queue dropped blocks. The record holds the tuning generation, which rises with every center-frequency call, the center frequency last programmed, a flag for a transfer that moved fewer bytes than requested, a flag for a block whose capture interval may overlap a retune, and the persistent shortfall of delivered samples against the sample clock.

A block is marked settled when no retune is running and it began at least 10 ms after the last retune call returned. The start of a block is its completion time minus its duration, which relies on the controller filling requests back to back. A refused frequency increments the generation and leaves the recorded frequency as it was. The shortfall compares the samples that arrived with the samples the sample clock implies since the first completed transfer, takes the minimum over the last eight blocks so that lateness a queue absorbs disappears while a loss persists, and reads zero below 2 ms of signal. A loss therefore appears eight blocks after it happened and stays in the record for the rest of the stream. The radio acts on the record so that its consumer does not have to. A block whose transfer was short or that is not settled is withheld. A capture ends, and a new one begins with the next block that is kept, when the tuning generation or the sample-rate epoch changed, when blocks were withheld, when the consumer's queue discarded a block, or when the shortfall rose. A loss is detected about eight blocks after it happens, so the capture that ends at the detection already holds the blocks that followed the loss.

## Measured behavior

All measurements were taken on one Blog V4 dongle at 2.4 MS/s in a debug build, with a harness that drives the device layer and the transport directly.

A center-frequency change takes about 55 ms inside the call (median 55.0 ms, range 54.4 to 70.8 ms over 20 retunes of 600 kHz between 90.4 and 91.0 MHz). The marker was a broadcast station at 90.705 MHz, whose energy moved between a band at +305 kHz and a band at -295 kHz, tracked in 1 ms steps. Samples keep the old tuning for about the duration of the call (40 to 62 ms after the call began, median 56 ms), and the transition is complete within 1 ms. The chunk holding the transition reached the consumer between 14 ms before and 4.5 ms after the call returned (median 4.8 ms before), so a consumer that discards the block in flight at the moment of the call sees new-frequency samples from the next block onward. All 20 retunes showed a clean transition, and none of 20 retunes to the frequency already set produced one. That experiment covers 600 kHz steps and a strong carrier, and other step sizes are reported below.

Completion callbacks arrive at the block spacing to within 0.2 ms when the system is otherwise idle. The median spacing equalled the block duration (5.01, 20.05 and 80.00 ms for 5, 20 and 80 ms blocks), the 99th percentile exceeded it by at most 0.1 ms and the maximum by at most 0.17 ms, across queue depths 2 to 16. Behavior under system load is reported below.

Sample loss was measured as the shortfall of delivered samples against the sample clock, which resolves 0.1 ms of lost signal when the consumer keeps up. With a single stall injected into the handler, the loss followed the stall length minus about (depth - 1) times the block duration: at depth 8 and 20 ms blocks the stream lost nothing for stalls up to 100 ms and 61 ms for a 200 ms stall, and at depth 4 and 80 ms blocks it lost 163 ms for a 400 ms stall and nothing for 200 ms. The ladder of stall lengths was coarse, so the lossless limit is bracketed by the fit and not located exactly. Under this model the default of 8 requests of 20 ms tolerates a consumer stall of about 140 ms, and a stall that outlasts that loses the remainder, which the sequence numbers cannot show, because they count blocks delivered to the router and a loss at the controller leaves the numbering intact. A consumer that does steady work on every block and the unplug path are reported below.

The acquisition record was checked against the same hardware. Over 20 retunes, no transition window lay in a block marked settled, one or two whole blocks after the transition were still marked unsettled, and no block reported an incomplete transfer. The block holding the transition started at least 15.3 ms before the call returned in every case, so these runs cannot separate settle margins between 0 and 15 ms, and the 10 ms margin is protection against variation that was not sampled, such as other step sizes. The generation after 40 calls was 40, because a call to the frequency already set reprograms the tuner and counts. With a stall of 200, 300 and 1000 ms in the stream's handler, the reported shortfall was 65.4, 162.5 and 860.2 ms against independent clock estimates of 66.1, 162.5 and 860.4 ms, first appeared eight blocks after the stall, and read zero for stalls of 0, 50, 100 and 120 ms and for three unloaded runs. Over 180 s of unloaded streaming the raw deficit stayed within a 0.25 ms band, with no trend that the band resolves, so the 2 ms tolerance holds for at least that long; a clock offset of 1 ppm would use it up in about 33 minutes, and runs longer than 180 s have not been measured. The transfer flag has been tested only against chosen byte counts, because no short transfer occurred on hardware.

The behavior of the radio as a program sees it was measured with a separate program that opened the dongle through the public interface and read its captures, built in release and run on the same dongle. The marker was a broadcast carrier at 90.70 MHz that stood about 30 dB over the median of the spectrum. Tuned below the carrier it lies at a positive offset in the baseband and tuned above it at a negative one, so every 0.85 ms window of every block could be classified by which of the two bands held more power. Over 24 retunes at each of three step sizes (400 kHz, 600 kHz and 1 MHz) the radio delivered 25 captures each time, and none of about 4,600 windows per step read as the tuning on the other side of the retune. The weakest correct window had a margin of 24 dB at the 400 kHz step, 15 dB at 600 kHz and 13 dB at 1 MHz. Twelve retunes to the frequency already set gave 13 captures and no wrong window, which shows that the classifier produces no flips of its own. Blocks spliced from the two tunings show what the classifier resolves: a window with 25 percent of its samples from the other tuning loses about 10 dB of margin, and one with half of its samples from the other tuning reads as the other tuning. At the 400 kHz step a quarter-contaminated window would therefore have stood out from the clean windows, and at the two larger steps only a window with about half its samples or more would have. A call to retune took 55 ms at the median and the first block of the new capture reached the consumer about 100 ms after the call began, at every step size. The measurement covers one location and one carrier.

Sample rate changes made while streaming (3.2 MS/s, 1.024 MS/s, 250 kS/s, 2.048 MS/s, 1.4 MS/s and 2.4 MS/s) each began one capture at the new rate, and the samples delivered per second of wall time matched the rate to within 0.01 percent. Manual gains of 0, 20, 30, 40 and 49.6 dB and automatic gain changed the signal level within a single capture, from an rms of 0.064 at 0 dB to about 1.1 from 30 dB upward, where the converter was clipping on the strong signals at this location. Unloaded, 20 s of streaming gave one capture, 99.9 percent of the sample clock, a worst gap between blocks at the consumer of 20.3 ms and no shortfall. With 36 busy processes on a 12-core machine, a load average of about 47 at its peak, the same 20 s gave one capture, the same share of the sample clock, a worst gap of 26.3 ms and no shortfall. This load did not cause a loss at the controller, so the shortfall path has been exercised on hardware only through stalls injected in the stream's handler. A longer run under load has not been made.

Consumer stalls were measured through the radio in a debug build. A stall of 50 ms or 120 ms in the consumer left one capture, and a stall of 300 ms or 1000 ms ended it and began another, which is the consumer's queue discarding blocks. Nine retunes from 10 MHz to 1.09 GHz, across the HF conversion of the Blog V4 and the VHF and UHF bands, each began exactly one capture at the new frequency. A tuner call made directly on the main actor stalled a 1 ms timer on it for 74 to 76 ms, and the asynchronous retune stalled it for 2.2 to 2.5 ms against a floor of 2.1 ms with nothing running. A second open of a dongle that is already open was refused, and the dongle opened again after the radio was closed and after it was released without being closed.

Unplugging the dongle during a stream was tried twice. In the first run the stream ended with a transfer failure (IOReturn 0xe00002ed, device not responding) and the registry had not yet reported the device terminated, so the cause was classified as a transfer error. For that reason the radio decides the cause some time after the first failed transfer, initially 250 ms. In the second run, made with that rule in place, the stream ended with the disconnected error, the bus held no dongle at that point, and a retune afterwards was refused.

The delay between the last delivered block and the registry's departure event was then measured over five unplugs, with a resolution of one 20 ms block. Four unplugs gave 117, 123, 142 and 170 ms, and in each the termination message ended the stream within 3 ms of the departure event. One gave 673 ms; there a transfer failed first, the 250 ms decision found the device still in the registry, and the unplug was reported as a transfer failure. The radio therefore decides the cause 1 s after the first failed transfer, which covers all five observations and delays the report of a transfer failure on a connected dongle by the same second. The five unplugs were made on one machine and one port, so 673 ms is the largest delay observed and the bound is unmeasured.
